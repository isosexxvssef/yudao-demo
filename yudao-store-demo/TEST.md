# 门店管理模块 - 测试说明

本文档详细说明门店管理模块的测试方案，覆盖多租户隔离、CRUD、Excel 导入导出、定时数据清洗等全部功能的测试用例。

---

## 一、前置条件

开始测试前，确保满足以下条件：

| 项 | 要求 | 验证方式 |
|----|------|---------|
| 后端服务 | 正常运行，端口 48080 | 浏览器访问 `http://localhost:48080/doc.html` 看 Swagger 是否可打开 |
| 前端服务 | 正常运行，端口 80 | 浏览器访问 `http://localhost` 看登录页 |
| PostgreSQL | 正常运行，数据库 `yudao_store` |  |
| Redis | 正常运行，端口 6379 | `redis-cli ping` 返回 `PONG` |



## 二、测试用例

### 测试 1：多租户数据隔离

| 项 | 内容 |
|----|------|
| **测试目标** | 验证租户A看不到租户B的数据，反之亦然 |
| **前置条件** | 数据库中租户A和租户B各至少有 1 条门店数据 |

**步骤 1：登录租户A**

在登录页的「租户」输入框填写 `租户A`，账号 `admin`，密码 `admin123`。

**步骤 2：验证门店列表**

进入「门店管理」→「门店列表」：

| 检查点 | 预期结果 |
|--------|---------|
| 列表中的数据 | 只显示 tenant_id=123（租户A）的门店 |
| 是否能看到 B901/B902 | 完全看不到租户B的任何门店 |

**步骤 3：租户A 创建编码为 B901 的门店**

点击「新增」，填入：
- 门店编码：`B901`（租户B已有的编码）
- 门店名称：`租户A也要B901`
- 其他字段任意

| 检查点 | 预期结果 |
|--------|---------|
| 保存结果 | 创建成功 ✅（因为跨租户，租户A里没有 B901） |

**步骤 4：租户A 再次创建编码为 A901 的门店**

| 检查点 | 预期结果 |
|--------|---------|
| 保存结果 | 提示「门店编码已存在」❌ |

**步骤 5：切换租户B**

退出登录，使用「租户B」 / `admin` / `admin123` 重新登录。

| 检查点 | 预期结果 |
|--------|---------|
| 门店列表 | 只显示 B901/B902，看不到租户A的任何门店（包括刚创建的 A901/B901 这条） |

| 检查点 | 预期结果 |

**2.4 编辑门店（编码冲突）**

编辑 TEST-001 时，将门店编码改为同租户已存在的另一个编码（如 A901）：

|--------|---------|

**2.5 按门店名称搜索**

在搜索栏「门店名称」输入关键字（如「A901」），点击搜索：

| 清空搜索并重置 | 点击「重置」恢复全量列表 |

**2.6 删除门店**

- 单条删除：在 TEST-001 行点击「删除」，确认弹窗
- 批量删除：勾选 2 条记录，点击顶部「批量删除」

| 检查点 | 预期结果 |

| 删除后列表 | 对应记录不再出现（逻辑删除，deleted=1） |
| 数据库检查 | `SELECT * FROM zy_store WHERE id = <id>` 仍存在，但 `deleted = 1` |

### 测试 5：定时数据清洗

| 项 | 内容 |
|----|------|
| **测试目标** | 验证手动触发清洗、清洗规则生效、日志记录、定时任务配置 |

> 测试前需要租户A 存在脏数据（可执行测试说明第 2 节的 SQL 插入）。

**5.1 查看当前脏数据（清洗前对照）**

```powershell
$env:PGPASSWORD="123456"
& "D:\PostgreSQL\18\bin\psql.exe" -h 127.0.0.1 -U postgres -d yudao_store -c `
  "SELECT id, store_code, store_name, platform, manager, phone FROM zy_store WHERE tenant_id = 123 AND store_code >= 'A903' ORDER BY id;"
```

应能看到：
- A903 门店名称两端有空格
- A903/A904 manager 字段有多余空格
- A903/A904/A906 phone 字段有 `-` / 空格
- A903 platform = `meituan`（应规范成美团）
- A904 platform = `美 团`（应规范成美团）
- A905 platform = `饿了么平台`（应规范成饿了么）
- A906 platform = `京东到家`（应规范成京东）

**5.2 手动触发清洗**

在前端页面「门店管理」→「数据清洗日志」点击「触发清洗」按钮。

> 或调用 API：
```powershell
# 登录获取 token
$body = '{"username":"admin","password":"admin123","captchaVerification":""}'
$r = Invoke-WebRequest -Uri "http://127.0.0.1:48080/admin-api/system/auth/login" -Method Post -Body $body -ContentType "application/json" -Headers @{"tenant-id"="1"}
$token = ($r.Content | ConvertFrom-Json).data.accessToken

# 触发清洗
Invoke-WebRequest -Uri "http://127.0.0.1:48080/admin-api/store/clean/trigger?triggerType=2" -Method Post -Headers @{"Authorization"="Bearer $token"; "tenant-id"="1"}
```

| 检查点 | 预期结果 |
|--------|---------|
| 弹窗结果 | 显示开始/结束时间、扫描数量 ≥ 6、修改数量 ≥ 4、执行状态=成功 |
| 响应时间 | 通常 ≤ 3 秒完成 |

**5.3 验证清洗结果（清洗后数据）**

再次执行 5.1 的 SQL：

| 字段 | 清洗前 | 清洗后 | 验证 |
|------|--------|--------|------|
| A903.store_name | `  有空格门店A903  ` | `有空格门店A903` | ✅ trim 生效 |
| A903.manager | ` 张 三 ` | 不变（内部空格不清理，仅 trim 首尾） | ✅ |
| A903.phone | `138-0000-0903` | `13800000903` | ✅ 去掉短横线 |
| A904.phone | ` 139 0000 0904 ` | `13900000904` | ✅ 去掉空格 + trim |
| A903.platform | `meituan` | `美团` | ✅ |
| A904.platform | `美 团` | `美团` | ✅ |
| A905.platform | `饿了么平台` | `饿了么` | ✅ |
| A906.platform | `京东到家` | `京东` | ✅ |
| B902.platform（租户B的） | `jd` | `京东` | ✅ 跨租户也清洗了 |

> 注意：A903/A904 manager 字段的**内部**空格（如 `张 三` 中间 1 个空格）不在清洗规则范围内，规则只是**首尾** trim，这是符合需求的。

**5.4 验证清洗日志**

前端「数据清洗日志」列表：

| 检查点 | 预期结果 |
|--------|---------|
| 最新一条日志 | 触发方式=「手动触发」（triggerType=2） |
| 开始/结束时间 | 都有值，结束 > 开始 |
| 扫描数量 | ≥ 全部活跃门店数（含租户B，8+ 条） |
| 修改数量 | ≥ 脏数据条数（如 4~6 条） |
| 执行状态 | 成功（status=0） |
| 错误信息 | 空（status=1 时才填写） |

**5.5 重复清洗不会重复修改**

再次点击「触发清洗」，对比前后两次日志的「修改数量」：

| 检查点 | 预期结果 |
|--------|---------|
| 扫描数量 | 不变（依然是全量） |
| 修改数量 | 应该大幅减少（0 或极小），说明无脏数据可清洗，没有无意义 UPDATE |

**5.6 再次制造脏数据验证幂等**

```sql
UPDATE zy_store SET platform = 'eleme', phone = '  111-222-333  ' WHERE store_code = 'A901' AND tenant_id = 123;
```
重新触发清洗 → 应成功把 `eleme` → `饿了么`，`phone` → `111222333`，修改数量至少 +1。

**5.7 定时任务配置（静态检查）**

打开 [StoreCleanJob.java](yudao-module-store/src/main/java/cn/iocoder/yudao/module/store/job/StoreCleanJob.java#L32)：

```java
@Scheduled(cron = "0 0 2 * * ?")  // 每天凌晨 2 点
public void cleanStoreData() {
    storeCleanService.clean(TRIGGER_TYPE_SCHEDULED); // triggerType=1
}
```

| 检查项 | 要求 |
|--------|------|
| Cron 表达式正确 | `0 0 2 * * ?` = 每天 02:00 执行 ✅ |
| 触发方式标记 | `TRIGGER_TYPE_SCHEDULED = 1`，日志中会标记为「定时任务」 ✅ |
| `@EnableScheduling` | 由 `yudao-spring-boot-starter-job` 自动启用，无需项目重复加 ✅ |

> **提示**：如需实际验证定时任务（不需要等到凌晨 2 点），可临时把 cron 改成 `0 * * * * ?`（每分钟执行），重启后端观察日志和清洗日志表。验证完成后改回 `0 0 2 * * ?`。
